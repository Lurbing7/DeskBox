# Dock 关注入口修正

## 调研报告
22:28 实机复现已取得证据：闪烁来源、左侧点击目标、随后正常操作的 Shell 激活事件均为同一 HWND、同一 PID/TID；左侧 SetForegroundWindow 返回成功且实际前台 HWND 一致。错误窗口和前台权限假设已排除。通知到达时原窗口隐藏、非最小化；系统恢复命令让它变成原生可见，但用户视频仍显示旧消息，说明原生可见/前台成功不能作为应用内容恢复的验收条件。Qt 文档区分 QWidget 显示状态与原生窗口，托盘激活会触发应用 activated 处理：[QWidget](https://doc.qt.io/qt-6.8/qwidget.html)、[QSystemTrayIcon](https://doc.qt.io/qt-6/qsystemtrayicon.html)。应用自身恢复路径仍待确认；询问用户正常入口是托盘还是任务栏按钮，不再换一条原生窗口显示 API 试错。
视频单帧已确认正常入口为右下角托盘微信图标。只读验证：通知 PID 中存在 Qt 微信托盘消息窗口；通过 Shell_NotifyIconGetRect 的 HWND/uID=0 得到有效图标区域；Windows UI Automation 可读取该托盘按钮，支持 InvokePattern。新方案限定微信适配：以通知 PID 定位实际注册托盘图标，通过系统 Invoke 激活应用自身处理，不再将原生恢复命令用于微信；失败保留通知，不启动新实例。不使用猜测的私有消息、发送输入或外部代码注入，不引入 WPF 产品依赖。官方依据：[Shell_NotifyIconGetRect](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyicongetrect)、[InvokePattern.Invoke](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationinvokepattern-invoke)。隐藏任务栏情况下按钮是否仍可定位需要实机验收。
实施与检查：新增 DockWeChatTrayActivation，以通知 PID、实际注册图标区域、Shell 托盘控件类型与唯一匹配定位；通过公开 UI Automation COM 接口调用 Invoke，不执行鼠标移动/点击，不调用程序启动。后台线程显式统一 PerMonitorV2 DPI 上下文，退出恢复原上下文；只读探测曾因 150% 缩放导致矩形不同坐标系，修正后仅匹配到通知进程的一个微信按钮。COM 指针/BSTR/GCHandle 均释放；未知微信窗口类、托盘折叠或控件不可获取时返回失败，不转回危险的隐藏窗口恢复。
专项验收：生产定位代码在真实托盘只读运行，唯一匹配及 InvokePattern 可用；相邻图标、空矩形、部分重叠拒绝检查通过；未触发实际托盘动作。一般应用原生恢复 4 项回归及 Shell 闪烁监听回归通过。Debug 构建 0 错误、22 个已有警告，已启动当前 Debug。微信新消息内容刷新与隐藏任务栏验收仍待用户实机复测，当前不标记完成或可上线。
最新状态：用户确认 22:07 之后的系统恢复命令方案仍复现空白页面。此前推断未证实，停止叠加行为修复，回到边界诊断。只读探测确认当前微信为 Qt/Chromium 多进程，所有微信进程 MainWindowHandle 为 0；同一 UI 进程存在多个隐藏 Qt 图标窗口及托盘消息窗口。仅凭进程名、窗口标题或可见状态无法选定聊天窗口。
本轮实施范围仅为诊断：记录通知原 HWND、PID/TID、窗口类、可见/最小化/启用状态、所有者与弹窗关系；记录左侧点击的目标和前台结果；记录同一通知进程随后通过任务栏激活的窗口。日志只存本机，不记录聊天内容或窗口标题。完成采集后才能决定下一次行为修复。真实消息无法自动生成，需用户重复左侧与任务栏操作一次。

## 问题澄清
最新反馈覆盖先前回退规则：左侧是独立临时入口，固定图标位置保留；仅激活收到通知的现有窗口，严禁启动新实例。固定应用在根目录和分类目录之间移入时清除原位置重复快捷方式。以目标与启动参数共同识别应用，保留不同参数入口；外部文件与程序本体不删除。提示统一为右上角红点，保留辅助文字。

### 本轮规划
通知按钮保存事件 HWND，点击后即使通知状态变化仍切换原窗口；失败保留通知并显示错误。导入先落盘验证，随后只清理当前 Dock 根目录和直属真实分类目录中的相同快捷方式；不遍历外部文件夹链接。已有重复入口保留根目录优先，移出项备份到本地忽略目录外的用户数据备份目录。快速检查并重新构建、重启。

### 22:07 视频反馈：通知打开空白页面
视频显示左侧入口打开微信空白内容页，任务栏入口随后正常。不能据此断言微信进程卡死。当前代码会强制 ShowWindow 隐藏所有者窗口，并可能选择进程 MainWindowHandle；它们不一定是任务栏通知对应窗口，也绕过了应用自己的恢复处理。此路径确认存在风险，真实微信内部原因未证实。
本次限定修复：撤销隐藏窗口强制显示与进程主窗口回退，仅向通知原 HWND 发送有超时保护的 WM_SYSCOMMAND/SC_RESTORE，由应用处理恢复；等待可见后激活该窗口或其可见、启用的模态弹窗。拒绝显示未知隐藏所有者，禁止启动新实例。参考 [WM_SYSCOMMAND](https://learn.microsoft.com/en-us/windows/win32/menurc/wm-syscommand) 与 [微软窗口切换说明](https://devblogs.microsoft.com/oldnewthing/20111107-00/?p=9183)，不宣称完全复刻任务栏内部逻辑。
验收计划：原生测试应用拦截恢复命令，验证触发应用恢复处理、隐藏窗口不会被直接强制显示、不会激活错误所有者；构建重启后微信真实来信仍需实机复测。
实施结果：通知激活改为异步、有界等待（恢复消息最多 300ms，随后最多 5 次、每次 80ms）；保留通知 HWND，不查任意进程主窗口，不强制显示隐藏所有者。测试最初暴露整个类 unsafe 上下文不能 await，已缩小 unsafe 至指针互操作方法，复构建通过。原生专项检查 4 项通过：收到恢复命令、拒绝恢复不强制显示、应用接受恢复后显示、过期句柄安全失败。测试环境前台切换返回 false，实际前台切换和错误所有者焦点验证未通过，不将这些计为通过。最终构建 0 错误、22 个已有警告。
